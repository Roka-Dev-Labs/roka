What prune_file actually keeps on LogHub

A rerun of the shipped engine — roka-mcp/lib/prune.js — on the 15 public LogHub 2k files. One 4,000-character budget, no query, no per-file tuning. Mean lines removed 98.3%. Character compression 70×. On the 11 files that contained a crash-regex line, at least one such line was still in the output.

By Roka Labs · Reading time ~6 min · Engine: prune.js as shipped

The problem: agents get the tail of a huge log

Coding agents are asked to read production logs. A LogHub 2k sample is already ~150K–595K characters. The MCP default budget is 4,000 characters. If the caller just takes the last 4,000 characters, anything earlier is gone.

On Thunderbird_2k.log the sshd bind failure sits at line 1,466 of 2,000 — 73% through the file. A naive tail -c 4000 never sees it. That is the failure mode this study measures against.

Scope of this note We measure compression and crash-regex retention under a character budget. We do not measure whether an agent then debugs the incident, and we do not claim semantic ranking. The default ranker is deterministic: collapse adjacent duplicates, then pack query → crash → neighbor → recency.

Method

On 10 Nov 2026 we ran the shipped function pruneText from roka-mcp/lib/prune.js — the same path MCP prune_file uses — against the public LogHub *_2k.log files from logpai/loghub. Zookeeper is a LogHub source and is not in this 15-file set.

Tool
prune_file(path, budget=4000). Arguments are path, optional budget, optional query. There is no force_keep flag.
Query
Empty. This run did not pass a query, so the query bucket was unused. Pack order was crash → neighbor → recency.
Budget
4,000 characters. Whole lines only. A protected line longer than the budget is kept whole and the overage is reported; that did not happen on these files.
Crash line
A line matching /\b(ERROR|FATAL|CRITICAL|Exception|Traceback|panic)\b/i. This is lexical, not a human incident label.

The three stages

  • Collapse. Adjacent identical lines merge to one line plus (xN repeated). Lines that differ by a host, block id, or datasource id do not collapse.
  • Rank. If a query is present, whole-word query hits pack first. Then crash-regex lines, then neighbors within ±2 of a crash line, then recency (later index wins).
  • Pack. Selected whole lines fill the budget, original order restored. Protected lines that do not fit are counted as omitted, not sliced.

Line counts are text.split("\n").length, the same split the engine uses. Three files (HDFS, HPC, Spark) end with a newline, so they show 2,001 lines. The other twelve show 2,000. Total: 30,003 lines / 4,178,984 characters.

Earlier site copy used a 92.2% mean (BGL 72.7%, HPC 74.4%, Apache 74.5%). That was a previous ranker. This page reports the shipped prune.js on the public 2k files.

Results

Unweighted mean of the 15 per-file line-removal rates: 98.3%. Characters in ÷ characters out: 70× (4,178,984 → 59,690). Files with ≥1 crash-regex line: 11. Files where ≥1 such line survived the pack: 11 / 11.

11 / 11 means “at least one matching line remained,” not “every matching line remained.” Apache had 595 crash-regex lines and kept 50; 1,393 protected lines (crash + neighbor) did not fit. Four files — Android, HealthApp, Spark, Windows — had zero crash-regex hits, so that cell is n/a, not a miss.

What prune_file actually returns

The MCP tool accepts path, optional budget, optional query. The result shape is the prune payload, not an invented ratio object.

# Same call as this study — no query, default crash regex inside prune.js
tool_call: prune_file(
    path="Thunderbird_2k.log",
    budget=4000
)

tool_result:
    originalLines: 2000
    prunedLines:   29
    originalChars: 325192
    prunedChars:   3965
    kept[].reasons: crash | neighbor | recency

On this machine the 15 LogHub files each pruned in 1–14 ms in Node. A 50,000-line synthetic file took 39 ms. No model calls.

What this does not prove

  • Not agent usefulness. We did not score whether Claude, Cursor, or GPT then finds the root cause faster. Compression and regex retention are the measured outputs.
  • Not “every error.” Crash-regex is whole-word ERROR|FATAL|CRITICAL|Exception|Traceback|panic. It hits Apache [error] and also Linux “FPU exception support” and BGL “parity error corrected.” Windows “Failed” does not match, so CBS failures in that 2k file are recency-only.
  • Not every crash line. Files with hundreds of matches omit the rest when they do not fit as whole lines (Apache 1,393 protected omitted).
  • Not query ranking. This LogHub run passed no query. Query-first packing is in the engine and is what the homepage 9-line demo uses; it is not what produced these 15 percentages.
  • Not semantic search. Default MCP ranker is collapse + query/crash/neighbor/recency. Hosted embeddings are an optional Pro path, not this run.
  • LogHub 2k only. These are the public 2,000-line samples, not the full original dumps. Results will move on JSON logs, or on a query that names a line the regex does not.

Conclusion

The shipped pruner is a character packer with a crash regex and optional query, not a log parser and not an incident summarizer. On the 15 LogHub 2k files, with budget 4,000 and no query, it removed a mean of 98.3% of lines, emitted 70× fewer characters, and on every file that contained a crash-regex line, kept at least one.

The Thunderbird check is the concrete case: tail -c 4000 misses the sshd bind line; prune_file keeps it because the line matches error. That is the claim. CLI prune is free; MCP prune_file needs a Pro API key.
