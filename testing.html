What we did — and why it matters

The table is the same MCP prune_file run published on the homepage and in the research note. Fifteen LogHub files, one budget, no per-file tuning. It measures whether lines — and real errors — survive a 4,000-character pack. It does not measure whether a model then solves the incident.

Same four stages on every dataset

Ingest LogHub *_2k.log samples, ~2,000 lines, untouched.
Collapse Consecutive duplicate lines merge into one line plus a count.
Keep Lines matching ERROR, FATAL, CRITICAL, Exception, Traceback, or panic are packed first.
Pack Remaining lines fit a 4,000-character budget. Overage is reported, not hidden.

Real logs, not mocks

LogHub is the standard benchmark used in log parsing research (logpai). Each dataset comes from a different system with its own timestamp format, log structure, and failure modes — the same diversity you hit in production.

Same rules, every file

No per-file tuning. Collapse consecutive duplicates, force-keep crash lines, then pack to 4,000 characters. The same prune_file path the MCP server ships.

Retention, not a story

The measured result is lines removed and whether a real error line survived. 11 of 11 sources that contained an error still kept one. That is not a claim that every warning, or a full incident narrative, was reconstructed.

What held up: Across the 15 files, 92.2% of lines were removed after dedup and the budget pack. Average compression is about 69× (roughly 276K characters in, 4K out, per file). On the 11 sources that contained a real error, a verbatim error line was still in the output. Checked by hand.

BGL (72.7%), HPC (74.4%), and Apache (74.5%) keep more lines because those files are less repetitive. That is the file, not a miss. Thunderbird is the live check: the same 4,000 characters, and sshd: Bind to port 22 stays with Roka and is missed by a naive tail.

Zookeeper is a LogHub file and is not in this 15-file table. Older write-ups that used an 8,000-token budget, or token totals such as 1.7M, are not this run.
